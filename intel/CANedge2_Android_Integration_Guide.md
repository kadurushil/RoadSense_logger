# CANedge2 → Android App Integration: Discovery, Logging & Local File Ingestion Guide

## 1. Purpose

This document captures everything established and tested so far for
integrating a **CSS Electronics CANedge2** into the existing Android
application.

The current target architecture is intentionally simple:

``` text
Automotive CAN Bus
       │
       ▼
   CANedge2
       │
       │ logs CAN frames to MF4 on SD card
       │
       ▼
CANedge2 Wi-Fi Web Server
       │
       │ HTTP / REST API
       ▼
 Android Phone
       │
       ├── discover CANedge2
       ├── identify current logging session
       ├── discover available MF4 files
       ├── download files
       ├── store files in Android app-private storage
       └── feed files into the existing CAN/MF4 processing pipeline
```

The important abstraction is:

> **The CANedge2 is currently a working networked log source. The
> Android application does not need to control CAN acquisition. It only
> needs to discover the logger, retrieve completed/available MF4 log
> files, persist ingestion state, and pass the files into the existing
> processing pipeline.**

This should be treated as the first implementation target. Do not
redesign the CANedge2 configuration or introduce a cloud/server layer
unless a later requirement demands it.

# 5. RTC / Time Synchronization

The CANedge2 RTC is configured for network synchronization.

Current configuration:

``` json
"rtc": {
  "sync": 2,
  "timezone": 0,
  "adjustment": 0,
  "tolerance": 30,
  "ntp_server": "*.pool.ntp.org"
}
```

`sync = 2` corresponds to network synchronization in the CANedge2
configuration.

The official CANedge2 documentation states that the RTC retains
date/time while the device is powered off and can be automatically
synchronized from supported sources.

### What has been tested

During the field test:

-   CANedge2 connected to the network.
-   Network time synchronization occurred.
-   Log directories were created using the expected time/session
    organization.
-   Log timestamps were observed to be populated correctly.
-   New folders were created for new connection/power sessions.

Therefore the current system already has a functioning time
synchronization mechanism.

### Important Android design decision

The Android application should **not become the source of truth for
CANedge2 RTC synchronization**.

Instead:

``` text
CANedge2 RTC
     │
     ├── network synchronization
     │
     ▼
CANedge2 generated timestamps
     │
     ▼
MF4 log files
     │
     ▼
Android validates/consumes timestamps
```

The application can compare logger time against Android/network time,
but should not attempt to rewrite logger time as part of normal file
ingestion.

# 11. Android Integration Goal

The existing Android application should gain a new CANedge ingestion
module.

The desired application-level flow is:

``` text
User starts CANedge session
        ↓
App checks Wi-Fi/network connectivity
        ↓
App discovers CANedge2
        ↓
App identifies device
        ↓
App verifies HTTP/Web Server availability
        ↓
App discovers available log folders/files
        ↓
App determines which files are new
        ↓
App waits for file stability/completion
        ↓
App downloads MF4 file
        ↓
App stores file in app-private storage
        ↓
App records ingestion state
        ↓
Existing MF4/CAN processing pipeline consumes file
        ↓
Processed data becomes available to the application
```

The key principle is:

> **Do not couple the existing CAN/MF4 processing code to the network
> transport.**

The transport should produce a local file. The existing processing
pipeline should continue to operate on a local file.

# 13. Device Discovery Strategy

Device discovery is one of the first pieces to implement.

The CANedge2 documentation indicates that the Web Server can be accessed
using the device hostname or assigned IP address.

The device ID is:

``` text
7AC5E17F
```

Therefore the first candidate should be:

``` text
http://7AC5E17F/
```

However:

> Do not assume that hostname resolution will always work on every
> Android hotspot/network configuration.

Use a layered discovery strategy.

## Discovery priority

### Step 1 --- Known hostname

Try:

``` text
http://7AC5E17F/
```

### Step 2 --- Previously discovered IP

Persist the last successful IP address.

Example:

``` text
lastKnownIp = 192.168.x.x
```

Try it first on subsequent connections.

### Step 3 --- Local subnet discovery

If hostname and cached IP fail:

1.  Determine the phone's current local network information.
2.  Determine the local subnet.
3.  Probe candidate addresses for TCP port 80.
4.  Check the HTTP response.
5.  Identify the CANedge device.

Do not hard-code:

``` text
192.168.1.x
192.168.43.x
192.168.0.x
```

The hotspot may use a different subnet.

The Android app should derive the subnet from the active network
interface.

------------------------------------------------------------------------

# 14. Do Not Identify a CANedge Solely by Open Port 80

Other devices may also expose HTTP.

Discovery should use an application-level verification step.

Conceptually:

``` text
TCP port 80 open?
       ↓ yes
HTTP request
       ↓
CANedge-specific response/API endpoint
       ↓
Device ID/status validation
       ↓
Device accepted
```

The exact CANedge API endpoint should be verified against the CSS
Electronics Web Server API documentation before implementation.

Do not invent API endpoints.

# 15. CANedge REST API

The CANedge2 documentation confirms that the Web Server exposes:

``` text
/api/
```

as a REST API.

The Android agent should investigate and document the exact supported
endpoints before implementing the client.

The API investigation must answer:

``` text
1. How do we obtain device information?
2. How do we list directories?
3. How do we list files?
4. How do we obtain file metadata?
5. How do we download a file?
6. Is there an endpoint for current RTC/device time?
7. Is there an endpoint for logger status?
8. Is there an endpoint indicating active logging?
9. Can the API distinguish an actively written file from a completed file?
10. What HTTP status codes and JSON schemas are returned?
```

Only after these are confirmed should the API client be written.

# 16. File Discovery Model

The Android application should not blindly download every file every
time it connects.

It needs persistent ingestion state.

Recommended conceptual state:

``` text
CanedgeDeviceState
------------------
deviceId
hostname
lastKnownIp
lastSuccessfulConnection
lastSuccessfulApiCheck
currentSession
rtcValidationState
```

and:

``` text
CanedgeFileState
----------------
deviceId
sessionId / folder
relativePath
fileName
fileSize
lastObservedSize
downloadState
localPath
processedState
checksum/hash if available
firstSeen
lastSeen
```

This allows the app to resume after:

-   phone restart
-   app restart
-   Wi-Fi disconnect
-   CANedge power cycle
-   partial download
-   interrupted processing

# 17. Session / Folder Handling

Testing showed that a new folder is created for each new logger
session/connection.

This is valuable.

Treat the folder/session structure as a first-class concept:

``` text
CANedge
   ├── Session A
   │     ├── MF4
   │     ├── MF4
   │     └── ...
   │
   ├── Session B
   │     ├── MF4
   │     ├── MF4
   │     └── ...
```

Do not assume that the newest folder is always the only folder that
matters.

The app should be able to:

``` text
discover sessions
        ↓
identify current session
        ↓
identify files not yet ingested
```

Historical files may still be useful if ingestion was interrupted.

------------------------------------------------------------------------

# 18. File Completion / Stability

The logger splits files every 10 seconds.

A file that appears in the Web Server may still be changing.

The Android app should therefore avoid:

``` text
file discovered → immediately process
```

Instead:

``` text
discover file
     ↓
record size
     ↓
wait
     ↓
check size again
     ↓
size unchanged
     ↓
consider file stable
     ↓
download/process
```

A stronger implementation can use:

``` text
HTTP metadata
+
file size stability
+
API/device logging state
```

if the CANedge API provides those signals.

The exact waiting interval should be configurable.

------------------------------------------------------------------------

# 19. Android Local Storage

The downloaded MF4 files should initially be stored in the application's
private/internal storage.

Conceptually:

``` text
Android app private storage
└── canedge/
    └── 7AC5E17F/
        └── sessions/
            └── <session-id>/
                ├── <file-1>.mf4
                ├── <file-2>.mf4
                └── ...
```

Advantages:

-   no unnecessary Android storage permission requirements
-   app controls lifecycle
-   safe from unrelated applications
-   easy mapping to ingestion state
-   straightforward integration with existing file-based processing

The exact directory mechanism should follow the existing application's
storage architecture.

Do not introduce shared/external storage unless the user explicitly
needs exported logs.

------------------------------------------------------------------------

# 20. Separate Downloaded Files From Processed Data

Use a clear distinction:

``` text
Downloaded
    ≠
Processed
```

Example:

``` text
downloadState = COMPLETE
processedState = PENDING
```

Then:

``` text
downloadState = COMPLETE
processedState = COMPLETE
```

This prevents duplicate downloads and duplicate processing.

The app should be restart-safe.

------------------------------------------------------------------------

# 21. Recommended Ingestion State Machine

Use a simple state machine.

``` text
DISCOVERED
    ↓
WAITING_FOR_STABILITY
    ↓
STABLE
    ↓
DOWNLOADING
    ↓
DOWNLOADED
    ↓
PROCESSING
    ↓
PROCESSED
```

Failure states can return to:

``` text
DOWNLOAD_FAILED
PROCESSING_FAILED
```

with retry logic.

Avoid marking a file as processed until the existing processing pipeline
has successfully completed.

------------------------------------------------------------------------

# 22. Download Safety

A download should use a temporary local filename.

Example:

``` text
000123.mf4.download
```

After a successful and verified download:

``` text
000123.mf4
```

This prevents the processing pipeline from accidentally consuming a
partially downloaded file.

Conceptually:

``` text
HTTP download
      ↓
temporary file
      ↓
download complete
      ↓
optional size/hash verification
      ↓
atomic rename
      ↓
available to MF4 processor
```

# 23. Existing Pipeline Integration

The most important architectural rule:

> **The CANedge module should terminate at a local MF4 file.**

Do not rewrite the existing MF4 processing pipeline to understand:

``` text
HTTP
Wi-Fi
CANedge
REST
network discovery
```

Instead create a small adapter:

``` text
CANedge Download Manager
          ↓
       Local MF4
          ↓
Existing MF4 Pipeline
```

This allows the existing pipeline to continue working independently.

The same processing pipeline could eventually accept files from:

``` text
CANedge
USB
manual import
other logger
cloud sync
```

without changing the CANedge integration.

# 24. RTC Validation Strategy

The Android app should validate timestamps, not become responsible for
setting them.

Suggested validation sequence:

``` text
CANedge discovered
       ↓
obtain device/API time if available
       ↓
compare with Android network/system time
       ↓
record offset
       ↓
discover MF4 files
       ↓
inspect MF4 timestamp/header
       ↓
validate expected time relationship
```

Store something similar to:

``` text
rtcValidation:
    status = VALID / UNKNOWN / INVALID
    androidTime = ...
    canedgeTime = ...
    offsetMs = ...
    validatedAt = ...
```

### Important limitation

The current testing proves that network RTC synchronization works, but
it does **not yet establish a guaranteed Android-visible RTC
synchronization status endpoint**.

Therefore:

``` text
RTC synchronization status API = TO BE VERIFIED
```

Do not invent a status field.

If the Web Server API does not expose RTC synchronization state, use
timestamp validation as an indirect check.

------------------------------------------------------------------------

# 25. Timestamp Validation

At minimum validate:

``` text
MF4 timestamp
        vs
Android current time
```

The exact acceptable tolerance should be configurable.

For example:

``` text
expected maximum clock offset = configurable
```

Do not hard-code a production threshold until the actual deployment
requirements are defined.

Also validate:

``` text
timestamp monotonicity
session ordering
file ordering
unexpected future timestamps
unexpected historical timestamps
```

Potential anomalies:

``` text
CANedge time far in the past
CANedge time far in the future
session folder timestamp inconsistent with MF4 timestamp
timestamps jumping backwards
duplicate/overlapping ingestion
```

These should be surfaced as data-quality warnings rather than silently
corrected.

# 26. Network Lifecycle

Android connectivity can change at any time.

The CANedge integration should respond to:

``` text
Wi-Fi connected
Wi-Fi disconnected
network changed
CANedge reachable
CANedge unreachable
CANedge IP changed
CANedge restarted
```

Do not rely on a single long-lived TCP connection.

Recommended behaviour:

``` text
Network available
      ↓
discover CANedge
      ↓
perform API health check
      ↓
sync/discover files
      ↓
download
      ↓
connection failure?
      ↓
persist state
      ↓
retry after network becomes available
```

The application must be able to resume without losing ingestion state.

# 27. Polling Strategy

For the first implementation, use controlled polling.

Example conceptual flow:

``` text
connect
  ↓
discover
  ↓
list sessions/files
  ↓
download stable new files
  ↓
wait
  ↓
repeat
```

Do not implement aggressive continuous scanning.

The CANedge is a logger, not a real-time streaming transport in this
architecture.

The initial objective is:

> **Reliable file ingestion, not live CAN streaming.**
